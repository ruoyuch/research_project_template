# Repository Guidelines

## Project Structure

- Dependency and tool configuration lives at `pyproject.toml`, `.pre-commit-config.yaml`, and `uv.lock` (committed; never edit `uv.lock` by hand).
- All reusable logic lives in the installable package `src/project_package_name/`. Paths and parameters are centralized in its `config.py` (`DATA_ROOT` defaults to `./data`, overridable via a gitignored `.env`); never hardcode paths elsewhere.
- `pipeline/` holds the scripts you run. Name them descriptively (not numbered); the run order is documented in the repo README. Each script is short orchestration only: load → call `src` functions → save. Logic belongs in `src/`, not in pipeline scripts.
- `notebooks/` is for exploration only; nothing downstream may depend on a notebook. Outputs are stripped on commit by nbstripout.
- Tests are in `tests/` and use small synthetic fixtures with known answers.
- `data/` (raw/intermediate/final) and `output/` are gitignored and never committed. `output/figures/` and `output/tables/` are machine-generated by the pipeline and must be fully reproducible by re-running it.
- `docs/private/` (draft, notes, references) is gitignored work-in-progress. `docs/public/` is tracked and public-safe: `manuscript.tex`, `slides.tex`, and their included figures.
- Figures for the paper: pipeline saves to `output/figures/`; copy the curated final exhibits into `docs/public/` as vector PDFs, siblings of the `.tex` file that includes them.

## Commands

- Use `uv` for Python and the virtual environment (Python is pinned to 3.12; `.venv/` is disposable — never edit or commit it).
- Run everything through `uv run <cmd>`; do not activate the venv or call `pip` directly.
- Use `uv add` to add every (non-standard-library) package imported anywhere in the code to `pyproject.toml`; commit the resulting `pyproject.toml` and `uv.lock` together.
- Run pre-commit hooks after any changes with `uv run prek run -a` (hooks: ruff lint+format, nbstripout, whitespace/large-file/private-key checks).
- Run the test suite with `uv run pytest`.
- CI (`.github/workflows/ci.yml`) runs `ruff check`, `ruff format --check`, and `pytest` on every push and PR; keep all three green.

## Version Control Guidelines

- Do not create or edit files unless the user explicitly tells you to do so.
- Work in git branches instead of `main`.
- Stage new files you create to ensure pre-commit hooks see them.
- Do not commit: allow the user to commit manually when they're ready.
- Never commit anything under `data/`, `output/`, or `docs/private/`, and never weaken `.gitignore` to do so.

## Code Guidelines

- Follow all code formatting and linting rules defined in `pyproject.toml` (ruff: E, F, I, B, UP; line length 100).
- Write human-maintainable and interpretable code.
- Do not over-engineer code: prefer simplicity and legibility.
- Use thorough code comments to explain "what" code does and "why" it does it that way.
- Use type annotations and complete numpy-style docstrings in all public and private functions.
- All code in `src/` requires thorough unit tests; pipeline scripts stay thin enough not to need them.

## Paper Guidelines

- The manuscript is `docs/public/manuscript.tex`; slides are `docs/public/slides.tex`. Work-in-progress drafts live in `docs/private/draft/` (gitignored).
- Use pdflatex to compile and natbib/bibtex for references.
- Keep LaTeX build/temp files out of git: compile into a gitignored `out/` directory rather than next to the source.
- Keep any figures or other included files as siblings of the `.tex` file.
- Prefer `\autoref` to `\ref`.
- Use `\enquote` for quote marks and `\textit` for italics; avoid boldface.
- Use `\citet` and `\citep` for textual and parenthetical citations, respectively; avoid `\cite`.
- Use en dash (`--`) for ranges of values.
- Use em dash (`---`) to offset adjunctive phrases stronger than those in parentheses.
- Ensure table columns' values right-align on the decimal.
- Avoid system fonts, instead use texlive-provided font packages.
- Avoid importing other packages.
- Compile often, check log for warnings/errors, and resolve them.

## Consistency

- Verify consistency of terminology, descriptions, and results across the paper and code.
- Verify paper's methods section text matches the analysis code: methods, units, calculations, equations, terminology, and data should match.
- Verify analysis code output matches the paper's reported numbers, tables, figures, equations, and units.
- Verify paper text's claims against the figures/tables' numbers, signs, rankings, labels, legends, captions.
